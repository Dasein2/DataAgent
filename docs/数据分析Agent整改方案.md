# 数据分析 Agent 整改方案

2026-11-23 · 评估版本 `49dd038` · 供产品、数据和研发评审

建议把常用查数改成按业务指标出数。模型识别用户要看的指标、维度和时间，服务端从已确认的业务定义生成 SQL、检查关联、执行查询。业务用户打开分析就能看到数字如何计算、数据覆盖到哪一天，并能从一个异常值追到原始证据。首期选一个 Doris 业务域，优先解决重复查表、失效连接和关联后重复计数。

## 1. 当前项目的问题在哪里

我核对了当前源码、仓库内的桌面和手机验收截图，以及 `data/history` 下 2026-11-19 至 11-20 的 17 个本地历史任务。13 个使用 Doris、4 个使用 MySQL，16 个连接的环境标记为非生产。调用次数按已结束的 `tool_finished` 事件计，失败按 `is_error` 计。耗时取任务开始至结束。这批历史记录早于本次评估版本，线上频率、当时的业务答案和当前版本的改善幅度仍需要独立对账。

| 观察到的现象 | 设计上的含义 |
|---|---|
| 111 次工具调用有 30 次报错。46 次 `query_execute` 调用中有 12 次报错，6 次报读取 `stream` 属性异常，另外 6 次在同一任务返回 `SESSION_UNAVAILABLE`，首末相隔约 39 秒。 | 故障分类和本任务熔断排第一。驱动异常的具体触发条件需要在目标版本复核。让模型继续改 SQL 无法恢复失效的连接。 |
| 本地派生 `result_transform` 失败 7/11 次，其中 6 次报本地关系名错误。目录概览失败 5/8 次、目录搜索失败 3/6 次，这 8 次均带已关闭连接的诊断。 | 常用本地计算可以直接接受结果 ID 和操作。目录连接池应能淘汰失效连接，并标明检索覆盖是否完整。 |
| 14 个任务标记成功，其中 6 个期间出现过工具错误。成功且调用过源查询工具的 10 个任务，中位耗时 50.7 秒，最长约 113 秒。 | 运行完成、正确恢复、业务数字验对是三个不同指标。生产错数率需要按问题和标准答案测量。 |

**表关系有一个可以直接从代码解释的缺口。** 模型侧的 `catalog_overview` 默认看 12 个对象，最多 20 个。已声明外键之外，命名推断要求同时看到来源表和目标表、字段以 `_id` 结尾、目标名吻合且有单列主键。当前 Doris 和 StarRocks 适配配置关闭二级索引和外键读取，该路径又只从索引提取主键。适配器返回的主键列表为空，这条命名推断规则在这两个引擎上也就匹配不到目标表。前端可以分页浏览目录，表详情的「关联」展示该表的出向外键。增加概览表数只能扩大可见范围。[概览实现](../src/db/session.ts#L998) · [引擎能力](../src/db/engines/profiles.ts#L95) · [主键读取](../src/db/engines/mysql.ts#L537) · [目录面板](../web/catalog.js#L452)

目录缓存属于单个数据库会话，默认五分钟。查询结果的显式复用匹配原 SQL 和行数限制。新会话可以加载已选业务资料，但用户上次核对过的关系没有结构化的复用入口。[缓存配置](../src/analysis/options.ts#L16) · [会话初始化](../src/db/session.ts#L139) · [结果复用](../src/db/session.ts#L328)

**口径和工具顺序主要由模型承接。** 业务资料支持版本管理和按连接选择，选中的 Markdown 被加入提示词。工具按连接能力注册，查表、抽样、执行、本地变换和图表管理多数由模型选择先后。现有 SQL guard 和 EXPLAIN 预检负责访问与成本，JOIN 用途、时间口径及聚合粒度仍主要靠提示词。任务成功以模型给出完整终答为主要条件。已有的只读执行、精确数值、本地结果血缘、截断保护和图表单元格引用适合继续作为底层能力。[资料注入](../src/agent/runtime.ts#L146) · [工具选择](../src/agent/tools.ts#L700) · [查询执行](../src/db/session.ts#L306) · [任务状态](../src/agent/runtime.ts#L457) · [图表引用](../src/artifacts/refs.ts#L4)

## 2. 建立跨会话可复用的业务目录

先让数据负责人用日常报表回答三个问题：这张表一行代表什么、这个指标按哪天算、按这个维度拆开还能不能加回总数。把答案存成服务端能检查的三类记录。

| 记录 | 第一个业务域需要维护的信息 | 在查数时的作用 |
|---|---|---|
| 表和字段 | 业务名和俗称、明细或汇总、一行的含义、业务键和组合键、事件时间与入库时间、时区、分区、更新水位 | 在同名 ODS、DWD、ADS 对象中选对明细或已汇总的数据源。水位未知时显示「覆盖日期待核验」。 |
| 表关系 | 两端字段、方向、1:1／多:1／1:多／多:多、租户键、生效区间、适用指标、证据来源和检查范围 | 提供从事实表到维度的可用路径。两个事实表需要先分别汇总到共同粒度。历史维度依据业务选择事件当时或当前版本。 |
| 指标 | 业务名称及同义词、负责人、公式、分子和分母、去重对象、默认时间、过滤项、可拆维度、单位、可加性和版本 | 同一个指标由同一份定义生成 SQL。收入能按互斥渠道加总，周独立用户需要在整周重新去重。 |

首次接入按权限分页读取元数据，后台分批建索引，优先已选业务域和报表常用表。新库可以立即做字段查找和单表探索，界面显示已索引范围。对没有关系声明的仓库，先从已授权的表定义提取键模型和分区，再对照现行业务报表。查询时用业务词、别名和关系邻域找少量候选，返回选择原因和仍缺失的信息。物理键、已有业务资料、负责人认可的报表 SQL 可以提供关系候选。对高频候选记录目标键重复率、未匹配率、关联前后行数与事实主键数，以及核验的分区和日期。在指标可加时，同时比较关联前后的金额。在预算内优先选择近期完整分区或只读副本，记录核验水位，重复利用仍有效的检查。窗口内的结果只支持该窗口的判断。数据负责人确认业务用途后，关系才能用于相应的正式指标。Doris 的 `DUPLICATE KEY` 属于排序键，允许重复，目录需单独记录其键模型。

关系分「候选」「在指定范围通过检查」「业务负责人已发布」三个状态，分别记录证据、适用窗口和负责人。若两条路径都成立但归因对象不同，两个定义应分别保留。

首版可沿用单实例部署，为业务目录使用独立 SQLite 表和文本索引。跨会话按账号、连接目标、数据库身份和有效权限隔离，只保存已授权的元数据及核验摘要。字段、权限、键或指标版本变化时，使受影响的路径与计划失效。业务资料页面增加「提出关系／口径 → 对照样例 → 发布版本」的入口，历史结论仍指向当时的定义。这样维护一次，后续会话可以直接复用。

## 3. 重设模型可调用的工具与路由

| 面向模型的操作 | 输入和返回 | 落地位置 |
|---|---|---|
| 查业务定义 | 输入问题、业务域和当前会话，返回候选指标、可用维度、关联路径、范围及歧义 | 组合现有目录搜索、批量描述、业务资料与本地索引。 |
| 按定义分析 | 输入指标 ID、维度、筛选、时间窗和比较期。服务端绑定表列并形成带版本的计划，执行后返回结果 ID、检查记录和可引用的数字 | 引擎适配层按方言生成 SQL，复用现有只读执行、成本预检、超时和审计。需澄清或成本受限时先返回原因。 |
| 基于已有结果计算 | 输入结果 ID，加筛选、分组、排序、占比等结构化操作。返回派生结果和父结果 ID | 常用操作由服务端生成本地 PostgreSQL 查询，输入关系固定绑定到 `data`。完整性、字段、粒度和数据时点都满足问题时才走此路。 |
| 呈现分析 | 输入结果 ID 和意图，如趋势、排名或贡献，返回主图、明细表及引用 | 复用 ECharts 和不可变图表。存快照、归档、重命名、工作区建视图等动作，在相应用户意图下开放。 |

**按问题决定调用顺序。** 一条已发布指标的普通查询可以在一次分析调用中完成选路、编译、执行、核验。模型只填业务参数。后台分别计量元数据请求、成本预检、业务 SELECT、本地派生和核验成本，避免把模型轮数或共享查询预算误读为源查询数。

| 用户意图或运行状态 | 运行策略 |
|---|---|
| 已知指标，范围明确 | 直接命中业务定义和已验证路径，通常争取一条业务聚合 SELECT。按原策略预检，复用同一有效计划的预检结果，保持源 SQL 在固定只读连接上串行。 |
| 追问「排个名」「换成折线」「看刚才那批」 | 优先读完整结果。数据范围足够时改排序或换图可跳过模型的重复规划。本地缺明细、缺分母、已截断或用户明确要求最新时，重新回源并记录原因。已分组的每日去重人数无法还原周去重。 |
| 问有哪些表、关系或字段 | 只查目录。碰到两个有效但含义不同的方案，只问会改变数字的一件事，如「按注册时渠道，还是下单时渠道？」。 |
| 新问题需要临时 SQL | 允许受控探索。先绑定真实表列、验证粒度，再编译方言和成本预检。日期函数、时区、空值、零分母和聚合规则由适配器处理。语法／字段错误只允许一次有新依据的修正，禁止同一失败计划循环提交。 |
| 源连接失效、超时或结果不足 | 对 `SESSION_UNAVAILABLE` 关闭本任务后续源工具，提供重连入口及已有证据。元数据连接故障则淘汰对应连接并重新验证只读权限。超时仅在发现有效分区条件或更合适数据源后重规划。无法支持结论时明确指出缺项。 |

把用户看到的状态分成执行进度和结论核验两行。数值报告的每个关键数字都绑定结果行或图表单元格。服务端按指标版本、关联核验、数据覆盖和比较期可比性生成「已核验／限定范围／待确认」及原因。对纯目录问题验证元数据即可。模型说明变化时引用对应的结果。观察数据仅支持相关关系时，解释原因的文字标为待验证假设。

一次源查询的核验有三个落点。执行前按实际引擎检查表列、函数、时间边界和聚合粒度，并判断这个维度是否会让同一事实出现多行。执行中沿用当前连接的只读、范围、超时、行数和字节数限制。执行后在同一快照或可比较水位上，将分组结果与独立的业务基准对账。按需触发额外核验并记入预算。数据仍在更新、水位未知或比较范围不同，界面应展示核验受限的具体原因。无图的数字也要支持从答案直接定位结果行，使用已有图表引用的交互方式。

## 4. 一道能验出静默错数的题

以下是构造的验收数据。一笔已支付订单金额 100 元，含两件商品，当期有两笔已入账退款 10 元、20 元。问题是「这笔订单当期净收款多少？」。如果把订单同时连接商品明细和退款明细，会得到 4 行，支付金额被加到 400 元，退款被加到 60 元。SQL 能成功执行，答案却会变成 340 元。

按新流程，净收款指标绑定支付和已入账退款。商品明细对于这道题没有用途，规划器省去这张表，将退款先按订单汇总，再与唯一订单连接。结果页应显示 **净收款 70 元＝支付 100 元－退款 30 元**，点 30 元可核对两笔退款。把两笔退款改成同额，再加入另一笔同额订单，可同时验出按金额 `DISTINCT` 导致的漏算。如果追问「按商品拆开」，则需要退款归属或分摊规则，界面应继续显示已核验的订单级净收款 70 元，并标明商品分摊所缺的口径。

### 5.1 按问题选图，按屏幕排版

| 用户想知道什么 | 首选呈现 | 计算和展示约束 |
|---|---|---|
| 一共多少，变化多少 | 单个核心数字、本期和对比期、绝对变化或变化率 | 显示单位。比率变化给百分点，基期为零时报告绝对变化并标明原因。 |
| 从哪天开始变化 | 同粒度时间趋势，标出最大变化点 | 显示业务时区、完整区间和数据截止时间。部分周期单独标注，缺失点留空。 |
| 哪个渠道、地区或产品贡献了变化 | 排序横条，按对总变化的贡献展示 Top N 和其余组 | 仅对可加指标做加总对账。比率展示分子、分母及各组比率，去重人数说明跨组重叠。 |
| 是普遍变化还是少数极端值 | 直方图、分位数或分组对照 | 显示样本量、单位、空值数量和区间边界。样本统计标出取样方式。 |
| 用户在哪一步流失，哪批人留下 | 事件顺序明确时用漏斗，留存用同期群热力图 | 写明去重实体、入口人数、观察窗口。尚未走完观察窗口的格子显示「观察中」。 |

**结果页布局草图**沿用上一节的构造数据。

```text
这笔订单的净收款是多少？                    已核验 · 查看依据

      70 元             100 元             30 元
      净收款            已支付             已入账退款 · 2 笔

支付 100 元，扣除两笔退款后净收款为 70 元。

[查看两笔退款]   [查看计算口径]   [按商品拆分]
```

「查看两笔退款」打开对应明细，「按商品拆分」先显示缺失的分摊规则。对于“近七天比上一周少了哪些活跃用户”一类问题，首屏改为同一用户标识下两期去重人数、变化量和流失人群规模。展示流失明细时沿用当前账号的访问范围。

桌面主区按需要放一个分析标题、一句结论和一张主图。指标、范围、对比期、数据截止时间排成一行。点趋势图上的日期时联动渠道图。点渠道条或「查看依据」时打开右侧抽屉，先看精确数值、计算式和对应的结果行，再展开涉及的表、JOIN 方向、核验结果和 SQL。切换图型沿用同一份结果。需要补查的情形见 5.3 节。缺少适用图形时直接展示数值或表格。另设「涉及哪些表」视图，仅展开当前指标的关系。边上写明连接字段、1 对多的方向和证据来源。点击两条都能连到渠道表的路径时，对比它们分别回答注册渠道还是下单渠道，并允许把选择保存为业务定义。

手机首屏显示结论、范围和主图，资产树收入导航抽屉，证据从底部展开。延续现有暖白底、深色正文和强调色，让关键数字使用等宽数字字形，图线直接标注系列名，当前序列与基准用实线／虚线区分。「待核验」同时给文字和图标。空结果、待确认、连接中断和加载完成使用独立界面状态。验收用 1440px 桌面和 390px 手机视口实际观察，记录用户找到分母和原始结果所需的时间与点击次数。

### 5.2 首期交互 · 从一天的变化查到两个原始数值

以支付订单为例。下表是用于开发和验收的模拟数据，按业务时区的支付日统计，每笔已支付订单只归属一个渠道。桌面左侧显示每日订单折线，右侧显示所选日期的渠道增减。手机先显示折线，渠道条紧接在下方。

| 订单渠道 | 11 月 19 日（单） | 11 月 20 日（单） | 较前日（单） |
|---|---:|---:|---:|
| 自然搜索 | 220 | 210 | −10 |
| 广告投放 | 165 | 90 | −75 |
| 直接访问 | 65 | 60 | −5 |
| **全部渠道** | **450** | **360** | **−90** |

1. **选日期。** 点 11 月 20 日，趋势线突出当天的点，标题显示「360 单，较前日减少 90 单」。渠道条共用零线和跨日期一致的刻度，减少向左、增加向右，条尾直接写出带符号的单数。键盘和触屏用户也可用日期选择器完成相同操作。
2. **核数字。** 点「广告投放 −75 单」，在抽屉并排显示两天的精确值和算式 `90 − 165 = −75`。两个操作数各自绑定结果行的 `value_ref`，可追到该次执行的 SQL。三个渠道合计减少 90 单，能解释降幅的构成。判断广告投放为何减少订单，还需要投放或转化数据。

### 5.3 区分视图操作和补查

| 已保存结果的情况 | 点击后怎么处理 |
|---|---|
| 选中日和对比日完整，均有「支付日 × 订单渠道」且指标可按渠道相加 | 从同一 `result_id` 派生趋势、差额及其来源，只更新选中日期和渠道。切日期、换图型、打开已有数值证据，新增模型调用和源库查询均为 0。 |
| 只有日总数，缺渠道或对比日期，结果被截断，或用户要求更新到新的数据时点 | 仍展示已知的总数或已覆盖的范围，标明所缺数据并给出「补查渠道」或「补查对比期」入口。用户选择后，沿用指标口径、时区和访问权限走第 3 节的查询流程，生成新的结果 ID。 |
| 有渠道字段，但各组有重叠、指标是比率或某日缺数 | 去重人数显示重叠限制，比率按组显示分子和分母。缺数留空，只有已确认的零值才显示 0。可加指标若渠道差额之和与核准的总变化不符，显示「待核验」及差额。 |

**改动位置。** 在图表编译层建立从每个增减值到本期、对比期结果行的映射，复用现有引用解析和数值来源界面。前端共用选中日期、渠道和缩放范围。趋势点以支付日为标识，横条以渠道为标识，排序后也能打开正确的证据。[图表编译](../src/artifacts/charts.ts#L216) · [引用解析](../src/artifacts/refs.ts#L66) · [数值来源](../web/index.html#L1856)

**动效与导出。** 目前视口更新用 `setOption(next, true)` 整体替换配置。点选更新时给系列稳定的 `series.id`，只更新选中标记和受影响的横条，过渡约 240 毫秒。开启系统「减少动态效果」时直接显示终态。用户切换后保留缩放范围，SVG、PNG 导出选定视图的终态，CSV 继续导出该快照的数据。[视口更新](../web/charts.js#L318) · [图型切换](../web/charts.js#L414) · [导出](../web/charts.js#L385)

## 6. 交付顺序和验收

排期假设为一名后端、一名数据工程师和一名前端，业务指标负责人可定期审阅。以下是一个业务域的试点估算，数据质量和负责人可用时间会影响日程。

| 阶段 | 交付内容 | 验收条件 |
|---|---|---|
| 第 1 周，恢复与基线 | 优先复核 Doris 驱动和元数据断连，区分连接、方言、字段、范围和成本错误。本地常用派生绑定结果 ID。建立旧版测量基线 | 断连回放中，确认失效后新发起的源查询工具调用为 0。完整结果的排序、分组在本地完成。各类失败能独立计数。 |
| 第 2–3 周，首个业务域 | 入选约 10 张高频表、8 个高频指标。发布业务目录、关系和方言模板，接入结构化分析入口 | 数据负责人签认第一批口径。覆盖无外键、同名表、复合键、一对多和双事实表场景。 |
| 第 4–5 周，结果页与灰度 | 以支付订单为首个场景，交付趋势选点、渠道增减、双期证据抽屉和手机布局，原有会话继续可读。在固定数据快照上对比两条路径，随后按连接灰度 | 达到下表门槛再扩大范围。发现关键错数时暂停该指标的「已核验」输出。按连接回切旧流程时标记为探索结果，保留新旧版本的证据以便复盘。 |

建立 50 道脱敏题，优先从常见提问和报表对账争议中取样。建议 20 道高频指标、15 道跨表、10 道口径歧义／证据不足、5 道故障恢复。数据负责人提供独立参考查询或手算值，标出应澄清、应阻断和可直接回答的题。相同模型、提示预算、时区、权限及冻结数据分别跑两版，每题至少 3 次；冷热目录、源数据查询和本地追问分别计时。准备多份数据变体，在重复明细、跨租户同 ID、跨时区日界、漏配维表、零分母和截断时检验结果。先在 Doris 目标版本验证，再按引擎单独出兼容报告。现有 [工具路由评测说明](tool-routing-eval.md) 可作为用例起点。

| 上线指标 | 建议试点门槛 |
|---|---|
| 业务答案正确率 | 可回答题中，口径、数值和证据都与标准一致的比例 ≥95%。无充分理由的弃答计为失败。 |
| 高风险错数 | 指定反例中，错误数字被标成「已核验」为 0 次。歧义题另行统计应追问命中率。 |
| 查询和等待 | 已建模的常见问题，首条业务 SQL 可执行率 ≥95%。同组 P90 从提问到首个可核验答案的时间比旧版下降 ≥40%。分别记预检、扫描、模型等待和本地计算，记录超时和弃答占比。 |
| 复用和恢复 | 已有结果完整且足以回答的追问，新增源业务 SELECT 为 0。已确认会话失效后，新发起的源查询工具调用为 0，同时记录失效前已在途的请求。 |
| 结果可用性 | 所有正式数值结论都能定位到对应证据。5 名试用者中至少 4 人在 10 秒内找到指标定义，并在两次点击内打开数字来源。 |

**动态联动专项验收**（第 4–5 周）

- 用 5.2 节模拟数据点选 11 月 20 日，再点广告投放。两次点击应看到 `90 − 165 = −75` 和两行来源，渠道差额之和必须等于 `−90`。检查工具与查询日志，新增模型调用和源库 SELECT 均为 0。
- 用只有日总数的结果重复操作，应显示「补查渠道」。记录点击补查前后的查询数，确认仅在用户选择后发起查询，新旧结果均可按各自 ID 复核。
- 在 1440px 桌面和 390px 手机视口依次缩放、切日期、选渠道和导出。检查缩放范围和选中项，逐项比对图上标签、证据数值及 SVG、PNG 的终态。用键盘重复选择，再开启「减少动态效果」，两种方式均应得到相同的结果。

第一轮预算优先投给 Doris 连接恢复、一个业务域的表粒度和指标定义，以及一组能识别重复计数的标准题。它们共同决定工作台上的数字有多大把握、需要等多久，以及用户能否自行复核。
